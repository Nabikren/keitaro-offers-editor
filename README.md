# Keitaro offers editor

Небольшая обёртка над Keitaro Admin API v1:

- **Создание кампании**: название, GEO и существующий оффер. Создаёт кампанию с двумя потоками:
  1) принимает указанные страны и редиректит на Google; 2) весь остальной трафик — на оффер (100%).
- **Редактор офферов кампании**: Fetch streams, добавление/удаление офферов, Bring back из архива,
  закрепление долей (pin), Cancel и Push to KT. Правки копятся в локальном черновике и попадают в
  Keitaro только по Push.

Стек: **FastAPI + SQLAlchemy 2 + Alembic + SQLite** (backend), **Vue 3 + TypeScript + Vite** (frontend).

## Требования

- Python **3.11+** (FastAPI 0.163 и SQLAlchemy 2.1 не поддерживают 3.10)
- Node.js **20.19+ или 22.12+** (требование Vite 8)
- Keitaro с Admin API и API-ключом. Для демонстрации без Keitaro есть локальный фейк (см. ниже).

## Настройка

```bash
cp .env.example .env          # Windows: copy .env.example .env
```

Заполните в `.env`:

| Переменная | Назначение |
|---|---|
| `KEITARO_URL` | адрес Keitaro **без** `/admin_api/v1`, например `https://tracker.example.com` |
| `KEITARO_API_KEY` | ключ Admin API (передаётся заголовком `Api-Key`, только из backend) |
| `CAMPAIGN_NAME_PREFIX` | **обязателен** и должен начинаться с `test_simonov_` (до 60 символов `A-Z a-z 0-9 _ . -`). Push и создание разрешены только для кампаний с этим префиксом; пустой, пробельный, некорректный или не начинающийся с `test_simonov_` префикс запрещает и то, и другое. Для разового прогона — уникальный префикс вида `test_simonov_smoke_<random>_` |
| `REDIRECT_URL` | куда редиректит GEO-поток (абсолютный http(s)-URL, по умолчанию `https://www.google.com/`). Крайние пробелы удаляются (`strip()`), пробелы и управляющие символы внутри значения и некорректный порт отклоняются. При проверке созданного потока URL нормализуется: регистр схемы и хоста, порт по умолчанию, завершающий `/`, скобки IPv6 сохраняются |
| `PUSH_STALE_SECONDS` | через сколько секунд незавершённый Push показывается как «возможно зависший». **Только предупреждение**: перехватить запись онлайн нельзя (см. «Зависший Push») |
| `DEFAULT_DOMAIN_ID` / `DEFAULT_GROUP_ID` / `DEFAULT_TRAFFIC_SOURCE_ID` | необязательные значения по умолчанию для формы |

`.env` не коммитится. Ключ не уходит во frontend, логи и сообщения об ошибках.

## Запуск

Сначала скопируйте `.env.example` в `.env` в корне проекта и заполните как минимум
`KEITARO_URL`, `KEITARO_API_KEY` и безопасный `CAMPAIGN_NAME_PREFIX`.

### Windows PowerShell


```powershell

npm run dev
```

## Как это работает

### Черновик и публикация

Для каждой связи «поток ↔ оффер» в SQLite хранятся две версии:

- **опубликованная** (`pub_*`) — то, что подтверждено чтением из Keitaro (после Fetch или Push);
- **черновик** (`status`, `share`, `pinned`) — то, что пользователь видит и правит.

Поток «грязный» (жёлтый), если черновик отличается от опубликованного. Состояния связи:

| Черновик | В Keitaro | Показ |
|---|---|---|
| active, доля как в Keitaro | есть | обычная строка |
| active | нет, раньше не было | «новый» → после Cancel строка удаляется (оффер в каталоге остаётся) |
| active | нет, раньше был | «возвращается» (Bring back) |
| removed | есть | серая строка 0%, «будет удалён» |
| removed | нет | **архив**: серая, 0%, кнопка Bring back |

`removed` — только локальное состояние. В Keitaro по Push уходит полный желаемый список активных
офферов; сам Offer из каталога не удаляется.

**Fetch** заменяет опубликованное и черновик данными Keitaro. Доли из Keitaro не пересчитываются.
Fetch запоминает версии потоков до сетевых запросов и применяет результат только если версии не
изменились (CAS). Если пока шёл Fetch кто-то отредактировал поток или начал Push — 409 с актуальным
состоянием, правка не теряется. Повтор `offer_id` в ответе Keitaro — явная ошибка, ничего не применяется.
Связи, которые редактор знал, но которых больше нет в Keitaro, переходят в архив и не теряются.
Если в кампании есть черновик, Fetch возвращает конфликт; заменить черновик можно только после подтверждения.

**Push**:
1. Атомарно помечает поток «публикуется» (условный UPDATE по версии и только из `idle`). Пока поток
   в состоянии `pushing` — независимо от того, сколько это длится, — правки, Fetch кампании и второй Push
   получают HTTP 423. Перехвата «зависшей» записи онлайн нет: иначе два исполнителя могли бы писать
   в Keitaro одновременно.
2. Перед каждым PUT заново читает поток **и его кампанию** в Keitaro и останавливается без записи, если:
   поток принадлежит другой кампании; актуальное имя кампании не начинается с префикса (например,
   её переименовали после Fetch); alias не совпадает с alias, под которым кампанию создало приложение;
   состав офферов изменился после последнего Fetch.
3. Сохраняет в БД точный снимок защищённых полей потока (`push_baseline`) и только затем выполняет
   `PUT /streams/{id}` только с полем `offers` (полный желаемый состав). Снимок хранится, пока Push
   не подтверждён: повтор, путь `already_applied` и Fetch сравнивают текущий поток именно с ним, поэтому
   побочный эффект записи, ответ на которую потерялся, не теряется. Если при повторе защищённые поля
   уже отличаются от снимка, а офферы ещё не применены, повторный PUT не выполняется.
4. Снова читает поток: черновик считается опубликованным, только если состав и доли совпали, а повторов
   `offer_id` нет.
5. Семантически сравнивает до и после все поля потока, которые редактор не должен менять:
   `campaign_id, type, name, position, weight, state, schema, action_type, action_payload, action_options,
   collect_clicks, filter_or, filters, triggers, landings, offer_selection, comments` (порядок элементов
   массивов и служебные `id/oid/stream_id/created_at/updated_at/next_run_at` не учитываются).
   Если что-то изменилось — результат `side_effect_detected` со списком полей и красный «СТОП» в UI.
   Подтверждённые офферы сохраняются как опубликованные, а дальнейший Push этого потока блокируется
   до явного Fetch.

Таймаут или 5xx после отправки — это «результат неизвестен»: выполняется сверка чтением, черновик
не теряется, ложного «опубликовано» нет. Повтор Push идемпотентен: если прошлая попытка уже
применилась, повторной записи не будет.

Каждая правка передаёт `expected_version`; запрос со старой версией получает 409, поэтому
запоздавший ответ не затирает более позднюю правку.

### Расчёт долей

1. Закреплённые (pin) доли не меняются.
2. Остаток `100 − сумма закреплённых` делится поровну между незакреплёнными активными офферами.
3. Целочисленный остаток получают первые по порядку: 3 оффера → 34/33/33; pin 25% + два → 38/37.

Отклоняется: сумма закреплённых > 100; все активные закреплены, но в сумме не 100;
незакреплённому офферу достался бы 0%. Удалить последний активный оффер нельзя.
Remove снимает pin, поэтому Bring back не может создать конфликт закреплённых долей.

### Зависший Push (crash recovery)

Если backend упал посреди Push, поток остаётся в `pushing`, и приложение не снимает это само.
Восстановление — офлайн, при **остановленном** backend:

```bash
cd backend
python -m app.recover
```

Сверка только читает Keitaro (`GET /streams/{id}`; клиент сверки не умеет писать) и для каждого потока
в `pushing` или с сохранённым `push_baseline`:
- сравнивает защищённые поля со снимком перед PUT и фиксирует побочный эффект;
- если офферы в Keitaro уже совпадают с черновиком, отмечает их опубликованными; если совпадают с прежним
  опубликованным — запись не применилась, черновик остаётся, Push можно повторить; иначе нужен Fetch;
- если поток удалён (404), помечает его `remote_missing`;
- снимает `pushing` и снимок. При ошибке чтения (кроме 404) поток остаётся как есть.

Одновременную работу backend и сверки исключает блокировка ОС на файле `<база>.sqlite3.lock`: её держит
запущенный backend, а при аварийном завершении процесса ОС снимает её сама.

### Создание кампании

Шаги `кампания → GEO-поток → поток оффера → проверка чтением` выполняются как задание с
`idempotency_key`; кнопка блокируется на время запроса. Результат каждого шага сохраняется.

- Выполнять задание может только владелец аренды (lease, `JOB_LEASE_SECONDS`): захват — условным UPDATE,
  поэтому два параллельных «Продолжить» не выполнят одинаковые POST. Если процесс упал, задание после
  истечения аренды доступно для продолжения.
- Перед каждым POST и после потерянного/некорректного ответа (таймаут, 5xx, 200 без `id`, не-JSON) —
  сверка: кампания по заранее сгенерированному `alias`, поток по позиции и имени **с проверкой полной
  ожидаемой формы** (включая `campaign_id`). Несколько кандидатов или кандидат с другой формой — конфликт.
- Перед любым `POST /streams` кампания (созданная, найденная по alias или из прошлой попытки) полностью
  сверяется с заданием: `type, name, alias, domain_id, group_id, traffic_source_id`.
- Конфигурация Keitaro проверяется до создания задания и до захвата аренды.
- Любая ошибка, включая внутреннюю, завершает попытку статусом `partial`/`failed`, а не `running`.
- Итоговая проверка строгая: тип кампании, alias, имя и выбранные домен/группа/источник; ровно два
  потока; у каждого `type, name, position, state, schema, action_type, action_payload, filters, offers`.

При частичном результате показывается, что создано, и кнопка «Продолжить». Автоматического
удаления созданных сущностей нет — в Keitaro нет транзакций на несколько запросов.

Форма потоков сверена с существующей кампанией тестового стенда:
поток 1 — `schema=redirect`, `action_type=http`, URL в `action_payload`, фильтр
`country/accept/["AU"]`; поток 2 — `schema=landings`, оффер с долей 100. Ротация кампании — по позиции.
Домен, группа и источник выбираются в форме из `GET /domains`, `/groups`, `/traffic_sources`.

GEO: обязательна одна страна (ISO 3166-1 alpha-2). Несколько кодов через запятую — небольшое расширение
по макету формы: все они попадают в один фильтр страны первого потока.

| Live-стенд, запись | ограниченный smoke на собственной кампании: создание, 4 Push, внешний remove связи, Fetch/archive/Bring back/Cancel | выполнено 2026-11-17, каждый Push подтверждён повторным чтением |

Ограниченный live-smoke выполнен на отдельной тестовой кампании с уникальным разрешённым префиксом.
Через приложение выполнено ровно 3 POST и 4 PUT: `50/50` → pin `25` и `25/38/37` →
remove до `25/75` → Bring back до `25/38/37`. После каждого PUT приложение перечитало поток;
ни одно из 17 защищённых полей не изменилось. В админке отдельно удалена только одна связь оффера:
Fetch перенёс её в архив, Bring back восстановил локальный черновик, а Cancel вернул опубликованное
состояние без дополнительного Push. URL стенда, API-ключи и внутренние идентификаторы не публикуются.

## Ограничения и допущения

- Семантика частичного `PUT /streams/{id}` (только `offers`) в спецификации не описана. На live-стенде
  2026-11-17 четыре таких PUT сохранили остальные 17 защищённых полей; приложение проверило это чтением
  после каждого Push. Это подтверждение поведения текущей версии стенда, а не гарантия API-спецификации.
- Связи, выключенные в Keitaro (`state=disabled`), сохраняются как есть и не участвуют в перераспределении.
- Поиск офферов идёт по кэшу каталога в SQLite (обновляется раз в 5 минут): `GET /offers` в Keitaro без фильтров.
- Один процесс backend; блокировка Push хранится в SQLite. Для нескольких воркеров нужна внешняя блокировка.
- Пользователи и роли, статистика, лендинги и прочие настройки потоков — вне объёма задания.
